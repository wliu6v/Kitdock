# Kitdock 架构方案

## 1. 总体选择

采用轻量多语言 monorepo：同一仓库存放多个工具及共享组件。顶层按职责分区，工具按名称或用途组织；语言只影响工具内部结构和包的实现方式。

“每个工具独立”指有独立入口、README、运行和构建命令，并不要求每个工具都有自己的 Git 仓库、Go 模块或可单目录复制运行。依赖共享组件的工具通常需要完整仓库才能从源码构建；发布给用户的产物应携带必要依赖。

不预设统一启动器、插件框架、全语言构建系统或后台服务。出现具体需求后再引入，避免运行一个小工具需要安装所有语言环境。

## 2. 扩展后的目录示意

以下是未来可能出现的示例，不代表已经实现，也不要求预先创建这些目录。

```text
kitdock/
├── README.md
├── go.mod                          # 出现首个 Go 工具时创建
├── go.sum
├── tools/
│   ├── files/
│   │   └── filehash/               # Go 工具示例
│   │       ├── README.md
│   │       ├── main.go
│   │       ├── internal/          # 工具私有实现
│   │       └── bin/               # 本地编译产物
│   ├── network/
│   │   └── api-probe/              # JS 工具示例
│   │       ├── README.md
│   │       ├── package.json
│   │       ├── src/
│   │       └── tests/
│   ├── data/
│   │   └── csv-clean/              # Python 工具示例
│   │       ├── README.md
│   │       ├── pyproject.toml
│   │       ├── src/
│   │       └── tests/
│   └── system/
│       └── dns-flush/              # 平台命令封装示例
│           ├── README.md
│           ├── macos.sh
│           └── windows.ps1
├── packages/
│   ├── config-go/                 # 能力 + 实现语言
│   │   ├── README.md
│   │   ├── config.go
│   │   └── config_test.go
│   ├── cli-js/
│   │   ├── README.md
│   │   ├── package.json
│   │   └── src/
│   └── tabular-python/
│       ├── README.md
│       ├── pyproject.toml
│       └── src/
├── scripts/
├── docs/
└── templates/
```

工具目录深度通常控制在 `tools/<name>` 或 `tools/<category>/<name>`，避免无限嵌套。跨用途的工具选择最主要类别，其他入口通过索引链接提供，不复制源码。重分类会改变包路径，因此分类稳定后不要频繁搬动。

一个工具也可以包含多种语言，例如 Go 主程序与 Python 数据处理脚本；它仍然只占一个工具目录，并在 README 中列出所有运行依赖。

## 3. 共享组件与依赖方向

允许 `tools → packages` 和明确、无环的 `packages → packages` 依赖。公共包不能依赖具体工具；工具之间不导入彼此的私有实现，需要共享的逻辑提取到公共包。

- 先在工具内部实现；出现第二个真实调用方、语义确实一致时提取。
- 组件按能力命名，例如 `config-go`、`cli-js`，避免无限膨胀的 `common` 或 `utils`。
- 公共组件有自己的 README、稳定入口及有意义的测试。不要把具体工具的业务参数塞进全局配置。
- 各语言使用本语言的包机制复用；同名能力不要求每种语言都实现一份。
- 跨语言优先复用数据格式、JSON Schema、测试样例，或通过明确的 CLI 协议调用已有工具。CLI 协议应说明标准输入、标准输出、错误输出、退出码和版本兼容性。
- 只有出现明确收益时才考虑 FFI 或常驻服务。小段语言相关代码可以分别实现，避免为了去重引入部署负担。

## 4. 各语言的组织方式

### Go：初期一个根模块

首个 Go 工具加入时，在仓库根目录创建一个 `go.mod`。所有 Go 工具和公共 Go 包共用模块；`packages/config-go` 是普通包，不另建 `go.mod`。工具通过 `<module-path>/packages/config-go` 导入。

仓库地址确定后再选择正式 module path。简单 CLI 可直接在工具目录放 `main.go`；工具较复杂或有多个入口时再增加 `cmd/<command>/`。

优点是共享包可直接引用、依赖统一、联动修改容易；代价是所有 Go 工具共用依赖版本和最低 Go 版本。各工具仍可分别构建为独立二进制。

只有出现独立发布 Go 库、依赖版本冲突或显著不同的工具链要求时，再拆成多模块并用 `go.work` 联合开发。届时每个模块必须声明可发布、可解析的依赖，不能只靠本地 workspace 恰好构建成功。初期不创建空 `go.mod` 或 `go.work`。

### JavaScript / TypeScript

每个工具和共享包维护自己的 `package.json`。只有一个 JS 工具时可独立管理；出现多个 JS 包及共享需求时，再统一包管理器并启用 workspace，将实际工具目录与共享包目录纳入成员列表。

内部依赖通过包名和包管理器的本地 workspace 机制连接，不跨目录直接导入另一个工具的 `src`。统一 workspace 后统一锁文件策略，不保留互相冲突的安装方式。对外发布时验证包内容和依赖解析，不能假设用户机器上有仓库符号链接。

### Python

需要打包或第三方依赖的工具、公共库各自拥有 `pyproject.toml`，工具使用独立虚拟环境。开发阶段可将仓库公共库以 editable 方式安装进工具环境；不要通过临时修改 `sys.path` 或依赖启动目录来共享代码。

发布时为共享库选择可安装的发行方式，并在干净环境验证依赖齐全；本地 editable 安装成功不等于发布成功。仅使用标准库的单文件脚本可以保持简洁，无须预建完整包结构。

### Shell / PowerShell / 外部命令

小工具可以直接提供脚本与 README。必须列出 Shell 版本、外部程序、权限要求和安装步骤。Bash 脚本不会自动成为原生 Windows 工具；需要 WSL/Git Bash 时标记为条件支持并写明限制。

若 Mac 与 Windows 分别提供入口，保持参数和输出语义一致。复杂逻辑优先集中在可跨平台实现中，平台脚本只负责薄封装。

## 5. 跨平台要求

默认设计目标为 Windows 和 macOS；Linux 可按工具实际情况支持。目标支持与已验证支持必须分开记录。

- 使用语言提供的路径、临时目录、用户配置目录与进程 API，不硬编码 `/tmp`、`/Users/...` 或盘符。
- 调用子进程时尽量传递参数数组，避免拼接 Shell 字符串；处理路径空格、中文、Unicode 和退出码。
- 不默认系统已安装 `bash`、`sed`、`curl`、`make` 等程序。外部依赖写入 README。
- 隔离平台差异，例如 Go 的平台文件、Python/JS 的平台适配模块，或分别提供 `.sh` 与 `.ps1`。
- 区分操作系统与 CPU 架构。二进制记录 Windows amd64/arm64、macOS amd64/arm64 中实际提供和验证的组合。
- 涉及文件操作时检查大小写、换行符、文件锁、权限、符号链接及覆盖行为。
- 编译成功只说明构建通过；真正标注“已验证”前，还需在对应系统运行测试和基本功能检查。

CI 落地时，跨平台工具使用 Windows/macOS 作业；只支持单个平台的工具在目标平台验证。修改公共包时验证所有受影响的工具，不能只跑公共包自身测试。具体 CI 配置在首个工具加入后编写。

## 6. 文档、工具链与发布

每个工具必须有 README，公共包也需 README。工具 README 使用仓库模板，包含用途、语言、功能、平台状态、依赖、安装、运行、配置、测试与限制。根 README 只保留导航与简要索引。

SDK 版本使用项目级 asdf 配置管理，不擅自更改全局版本；具体版本在真实工具加入时确定。Windows 的环境安装另给原生可执行步骤，不把本机的 asdf 使用习惯当成最终用户的必备条件。

开发构建产物放各工具的 `bin/`，发行归档可使用工具自己的 `dist/`。未来启用版本控制时将产物、虚拟环境、依赖安装目录及本地配置加入忽略规则，保留锁文件和配置示例。

按工具发布产物，用户只安装需要的工具；共享包改动影响到哪些工具，就对这些工具重新验证。若采用独立版本，可使用 `<tool-name>/vX.Y.Z` 标记工具版本；发布规则在实际需要发布时落实。

## 7. 实施顺序

1. 当前仅保存架构文档、目录职责说明和 README 模板。
2. 加入第一个真实工具，建立该语言的最低必要工程配置。
3. 加入第二个工具时，根据真实重叠提取共享包。
4. 建立目标平台测试，记录实际验证结果。
5. 工具数量增长后，再增加用途分类、workspace 或自动化索引。

整体搬迁时复制完整 `kitdock/` 即可。当前方案没有绝对本机路径、父目录依赖或外部软链接；后续从其他位置迁入工具时，需要另行梳理其配置、数据和外部依赖。
